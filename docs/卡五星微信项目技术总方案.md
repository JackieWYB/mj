# 卡五星微信项目《技术总方案》

## 0. 目标与范围
- **产品形态**：
  - 对局：`Cocos Creator` 微信小游戏（实时网络对战）。
  - 外围：微信小程序页面（大厅、活动、战绩、商城、公告、客服）。
- **玩法范围**：湖北孝感“卡五星”核心规则 + 常见地方扩展（番型、房规参数化）。
- **技术目标**：
  - 对局稳定（断线重连成功率高、作弊风险可控、状态一致性强）。
  - 业务可运营（活动配置化、灰度发布、监控告警齐全）。
  - 支撑商业化（微信支付合规、商城与增值服务闭环）。

## 1) 系统架构图（文字版）

### 1.1 总体分层
1. **接入层**
   - 微信小程序前端
   - 微信小游戏前端（Cocos）
   - API 网关（HTTPS/WSS，鉴权、路由、限流）
2. **业务服务层**
   - 账号服务（登录、用户档案、资产）
   - 匹配服务（快速匹配、段位匹配、机器人补位策略）
   - 房间服务（建房、解散、座位管理、房间生命周期）
   - 对局逻辑服务（规则判定、出牌流程、结算）
   - 俱乐部服务（俱乐部管理、房间组织）
   - 战绩服务（战绩查询、统计）
   - 回放服务（事件流存储、回放下载）
   - 支付/商城服务（商品、订单、支付回调、发货）
   - 活动运营服务（活动配置、任务系统、公告）
   - 风控服务（设备、行为、策略评分）
   - 客服与消息服务（公告、邮件、客服入口）
3. **基础设施层**
   - MySQL（事务与结构化数据）
   - Redis（会话、缓存、队列、分布式锁）
   - 对象存储（回放文件、日志归档）
   - MQ（异步解耦：战绩落地、风控、支付通知）
   - 配置中心（动态配置、灰度开关）
   - 日志与监控（ELK/ClickHouse + Prometheus + Grafana）

### 1.2 关键调用链（典型对局）
- 小游戏客户端 → 网关（WSS）→ 房间服务（进房）→ 对局服务（发牌/轮转/结算）
- 对局服务 → MQ：
  - 战绩服务消费落库
  - 回放服务消费事件并归档
  - 风控服务消费行为流做评分
- 小程序页面 → 网关（HTTPS）→ 战绩/活动/商城/俱乐部服务

### 1.3 模块输入/输出/依赖（核心）
| 模块 | 输入 | 输出 | 依赖 |
|---|---|---|---|
| API网关 | HTTP/WSS请求、token | 路由后的内部RPC请求 | 账号服务、限流组件、服务发现 |
| 匹配服务 | 匹配请求(规则/段位/地区) | 房间分配结果(roomId, seat) | Redis、房间服务 |
| 房间服务 | 建房/入房/离房/解散请求 | 房间状态、成员列表 | 对局服务、Redis、MQ |
| 对局服务 | 玩家动作(出牌/碰杠胡/托管) | 广播事件、结算结果 | 规则引擎、房间服务、MQ |
| 战绩服务 | 结算事件 | 战绩列表、统计报表 | MySQL、对象存储 |
| 回放服务 | 对局事件流 | 回放ID、回放数据下载 | 对象存储、MySQL |
| 风控服务 | 行为日志、设备信息 | 风险分、处置建议 | Redis、策略引擎、画像库 |
| 商城支付服务 | 下单请求、微信支付回调 | 订单状态、资产发放 | 微信支付、MySQL、MQ |
| 配置中心 | 配置发布操作 | 生效配置版本 | 灰度系统、各业务服务 |
| 日志监控 | 服务日志、metrics、trace | 仪表盘、告警事件 | Prometheus、日志平台 |

## 2) 客户端工程拆分

## 2.1 Cocos Creator（小游戏）模块划分

1. **UI层（LobbyBridge + InGame UI）**
   - 输入：状态机状态、网络事件、用户点击
   - 输出：UI指令、动作请求
   - 依赖：状态机、网络层、资源管理

2. **渲染层（2.5D表现）**
   - 内容：2D精灵 + 透视变换 + 阴影/高光 shader + 分层遮挡
   - 输入：牌桌状态（手牌/桌牌/方向）
   - 输出：渲染帧
   - 依赖：动画系统、资源包管理

3. **动画系统（Tween/Timeline）**
   - 输入：业务事件（摸牌、出牌、碰杠胡、结算）
   - 输出：动画回调事件
   - 依赖：渲染层、音效层

4. **音效系统**
   - 输入：事件ID、本地设置
   - 输出：BGM/SFX播放
   - 依赖：资源管理

5. **网络层（WSS）**
   - 输入：业务请求对象
   - 输出：协议消息、重连状态
   - 依赖：网关协议、心跳模块、重试队列

6. **客户端状态机（FSM）**
   - 状态：`Idle -> Matching -> RoomReady -> Dealing -> Playing -> Settlement -> Replay`
   - 输入：服务端事件、用户操作
   - 输出：可执行动作集（仅允许当前状态动作）
   - 依赖：规则模块、UI层、网络层

7. **规则模块（轻校验）**
   - 输入：本地牌面与服务端回包
   - 输出：可操作提示（可碰/可杠/可胡）
   - 依赖：服务端规则版本号
   - 说明：仅做提示与一致性校验，最终裁决在服务端

8. **回放模块**
   - 输入：回放事件流（压缩包）
   - 输出：时间轴控制（暂停/快进/跳转）
   - 依赖：渲染层、动画系统

### 2.2 微信小程序页面模块
1. **大厅页**：用户信息、资产、玩法入口、匹配入口、公告摘要
2. **活动页**：活动列表、任务进度、奖励领取
3. **商城页**：商品展示、下单、支付、发货展示

## 3) 关键技术点设计

### 3.1 帧同步 vs 状态同步
- **结论**：麻将推荐 **状态同步（事件驱动）**，不采用高频帧同步。
- 原因：
  - 动作离散（摸/打/碰/杠/胡），天然回合制。
  - 带宽小、易重放、对弱网更友好。
  - 服务端权威裁决简单。

### 3.2 断线重连
- 客户端断线后进入`Reconnecting`状态，重连网关时携带：`uid + sessionToken + lastAckSeq`。
- 服务端返回：
  - `snapshot`（当前桌面完整快照）
  - `deltaEvents(lastAckSeq+1..current)`（增量事件）
  - `serverTime`（校准）
- 客户端先应用快照，再按seq补增量，恢复到最新状态。

### 3.3 状态一致性
- 所有对局事件统一分配单调递增`seq`。
- 客户端只按`seq`顺序应用；乱序缓存，缺包等待重传。
- 每N个事件生成状态哈希（`stateHash`），客户端与服务端对比，异常触发强制同步。

### 3.4 消息幂等与可靠投递
- 客户端请求带`clientMsgId`（UUID+递增序号）。
- 服务端维护`uid+clientMsgId`去重窗口（Redis set/hash，短TTL）。
- 广播消息采用`seq+ack`机制：
  - 客户端定时上报`lastAckSeq`
  - 服务端按需重发未确认窗口

### 3.5 房间状态机（服务端）
- `Created -> Waiting -> ReadyCheck -> Dealing -> Playing -> Settlement -> Dissolved`
- 转换由事件驱动（超时、玩家动作、系统事件）。
- 每个状态定义允许命令白名单，非白名单请求直接拒绝并记风控日志。

### 3.6 心跳与网络抖动处理
- 心跳周期：3~5秒；超时阈值：15秒（可配置）。
- 弱网策略：
  - 客户端自适应超时（RTT分位数）
  - 操作请求短重试（幂等保障）
  - UI提示“网络波动，已自动重连”
- 托管策略：连续超时进入托管，恢复后可取消托管。

## 4) 数据与存储设计

### 4.1 MySQL 关键表建议
1. `user_profile`
   - `uid(pk)`, `openid`, `nickname`, `avatar`, `level`, `created_at`, `status`
2. `user_asset`
   - `uid(pk)`, `gold`, `diamond`, `ticket`, `updated_at`
3. `room_info`
   - `room_id(pk)`, `mode`, `rule_set`, `owner_uid`, `state`, `created_at`, `expired_at`
4. `room_player`
   - `id(pk)`, `room_id`, `uid`, `seat`, `join_at`, `leave_at`
5. `game_round`
   - `round_id(pk)`, `room_id`, `start_at`, `end_at`, `winner_uid`, `result_json`, `replay_id`
6. `game_action_log`（可冷热分离）
   - `id(pk)`, `round_id`, `seq`, `actor_uid`, `action_type`, `payload`, `ts`
7. `record_summary`
   - `id(pk)`, `uid`, `round_id`, `score_delta`, `rank`, `created_at`
8. `shop_order`
   - `order_id(pk)`, `uid`, `sku_id`, `amount`, `wx_pay_id`, `status`, `created_at`, `paid_at`
9. `risk_event`
   - `id(pk)`, `uid`, `device_id`, `event_type`, `risk_score`, `detail`, `created_at`

### 4.2 Redis 键设计建议
- 会话：`sess:{uid} -> token/meta`（TTL）
- 匹配池：`match:{mode}:{segment}`（zset）
- 房间在线：`room:{roomId}:online`（set）
- 房间快照：`room:{roomId}:snapshot`（string/hash）
- 幂等去重：`idem:{uid}:{clientMsgId}`（setex）
- ACK游标：`ack:{roomId}:{uid} -> seq`
- 风控速率：`rate:{uid}:{api}`、`rate:{device}:{api}`

### 4.3 对象存储
- 回放文件：`replay/{yyyy}/{mm}/{roundId}.bin`
- 对局归档日志：`archive/game-log/{date}/{roomId}.jsonl.gz`
- 客户端资源热更包：`assets/{channel}/{version}/...`

## 5) 安全与反作弊

### 5.1 服务端权威
- 发牌、可操作集合、胜负判定、结算全在服务端。
- 客户端上行仅提交“意图动作”，服务端校验状态与规则后执行。

### 5.2 客户端校验与防篡改
- 协议签名（时间戳+nonce+签名）防重放。
- 客户端关键资源完整性校验（hash清单）。
- 关键逻辑混淆与反调试（不作为最终防线）。

### 5.3 频率限制与设备指纹
- 网关限流：按`uid/ip/device`三维限速。
- 设备指纹：机型、系统版本、网络特征、安装标识（遵循隐私合规）。
- 异常策略：高频建房/解散、秒操作、异常胜率触发二次验证。

### 5.4 作弊检测策略
- **实时规则**：非法动作、超时模式异常、重复消息攻击。
- **离线模型**：
  - 同IP/同设备多账号关联图谱
  - 异常胜率与配合行为检测（团伙）
  - 回放抽检 + 人工复核工单
- 处罚分级：提醒 → 限制匹配 → 临时封禁 → 永久封禁。

## 6) 可运维方案

### 6.1 配置热更新
- 统一配置中心（玩法参数、活动开关、风控阈值）。
- 配置版本号 + 生效时间 + 回滚版本。
- 服务订阅变更事件，灰度比例生效。

### 6.2 灰度发布
- 维度：用户白名单、渠道、版本号、地域。
- 流程：5% -> 20% -> 50% -> 全量，关键指标守门。

### 6.3 日志、链路、告警
- 日志：结构化JSON，包含`traceId`, `uid`, `roomId`, `roundId`。
- 链路追踪：网关->服务->DB/MQ 全链路trace。
- 告警：延迟突增、错误率、掉线率、支付回调异常、消息堆积。

### 6.4 核心指标（SLO建议）
- 网关QPS、P95/P99延迟
- 对局消息广播延迟（P95）
- 掉线率、重连成功率
- 对局完成率（开局到结算）
- 匹配耗时（平均/P95）
- 支付成功率、发货成功率
- 风控命中率与误杀率

## 7) 里程碑规划（MVP -> 公测 -> 商业化）

## 7.1 MVP（可内测）
**目标**：可稳定打完一局，覆盖核心闭环。  
**功能清单**：
- 微信登录、基础大厅
- 快速匹配、好友房
- 卡五星核心规则（可参数化最小集）
- 结算、基础战绩
- 断线重连、托管
- 基础日志与监控

**风险点**：
- 规则边界漏判
- 弱网重连状态不一致
- 房间生命周期异常（僵尸房）

## 7.2 公测版本
**目标**：可规模化运营，支持社交与活动。  
**功能清单**：
- 俱乐部系统
- 完整战绩与回放
- 活动中心、公告、客服入口
- 风控1.0（限流+规则检测）
- 灰度发布与配置热更

**风险点**：
- 活动高峰带来瞬时流量冲击
- 回放存储成本增长
- 风控误杀导致用户投诉

## 7.3 商业化版本
**目标**：收益闭环与精细化运营。  
**功能清单**：
- 商城、订单、微信支付合规接入
- 成长线/任务体系
- 风控2.0（画像+模型）
- 数据看板（留存、ARPU、付费转化）
- 多版本灰度与A/B实验

**风险点**：
- 支付合规与审核节奏
- 商业活动与玩法公平性的平衡
- 数据治理与隐私合规成本

## 8) 服务接口清单（后端内部RPC示例）

### 8.1 网关 <-> 账号服务
- `Auth.VerifyToken(token) -> {uid, expireAt}`
- `User.GetProfile(uid) -> profile`

### 8.2 网关 <-> 匹配/房间
- `Match.Enqueue(uid, mode, ruleSet) -> ticketId`
- `Match.Result(ticketId) -> {roomId, seat}`
- `Room.Join(uid, roomId) -> roomSnapshot`

### 8.3 房间 <-> 对局服务
- `Game.StartRound(roomId)`
- `Game.ApplyAction(roomId, uid, action, clientMsgId) -> {seq, events[]}`
- `Game.GetSnapshot(roomId, uid) -> snapshot`

### 8.4 对局事件异步流
- Topic: `game.round.settled`
- Topic: `game.action.stream`
- Topic: `risk.behavior.event`

### 8.5 商城与支付
- `Shop.CreateOrder(uid, skuId) -> orderId, prepayInfo`
- `Payment.Notify(wxTxn) -> ack`
- `Asset.Grant(uid, item, amount) -> result`

## 9) 依赖关系总览（简表）
- **小游戏对局**依赖：网关、房间服务、对局服务、回放服务。
- **小程序大厅**依赖：账号、活动、商城、战绩、公告服务。
- **风控服务**依赖：网关日志、对局事件流、设备画像库。
- **战绩与回放**依赖：对局事件MQ、MySQL、对象存储。
- **运营活动**依赖：配置中心、账号资产、消息通知。

> 建议技术栈（可选）：Go/Java（服务端） + MySQL + Redis + Kafka/RabbitMQ + Kubernetes + Prometheus/Grafana + ELK/ClickHouse。
